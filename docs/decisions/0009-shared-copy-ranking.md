# 0009: 共有プロンプトのコピー数を数え、公開ランキングを出す

- 日付: 2026-09-09
- 状態: 採用
- 関連: [0007](0007-prompt-sharing.md) / [0002](0002-server-only-data-access-rls-as-defense.md) / [0006](0006-service-role-grants.md)

## 背景

「シェアされて最も多くコピーされたプロンプトをランキング形式で表示し、オフラインでも
見られるようにしたい。10 位までは誰でも、ログインすると 100 位まで」という要望。
プロダクトの訴求を「X でシェアして広がる」に寄せたので、広がった結果が見える場所が要る。

[0007](0007-prompt-sharing.md) の時点では「アクセス数は記録しない」「ログインなしで
DB の中身を返す経路は `/s/<token>` だけ」としていた。これはその両方を意図的に覆す。

要件の確認結果:

- 置き場所: **公開ページ `/ranking`**（`/prompts` はログイン必須なので、10 位まで誰でもは満たせない）。
  `/prompts` のサイドバーと LP からリンクする
- 数えるもの: **`/s/<token>` で受け取った人がコピーした回数**。同じブラウザの連打は 1 回。
  持ち主が一覧でコピーしても数えない
- 集計: 全期間累計。表示は タイトル / 本文の冒頭 / タグ / コピー数
- オフライン: `/ranking` だけ Service Worker でキャッシュする

## 決定

### 1. 共有は「公開」を意味する

ランキングに載る = 誰でも見つけられる。共有リンクは手動で停止しない限り有効なので、
**1 回でもコピーされた共有プロンプトは、停止するまで公開一覧に出続ける**。
停止すればランキングからも消える（既存の共有も同じ扱い）。
共有しただけ（コピー 0 件）では載せない。

### 2. カウンタは別テーブル `prompt_share_stats` にプロンプト単位で持つ

- `prompts` の列にしない: `set_updated_at` トリガーが無条件に `updated_at = now()` を
  書くので、+1 のたびに一覧の並び順と共有ページの「最終更新」が動いてしまう
- `prompt_shares` の列にしない: 停止→再共有は新しい行になる（0007 §2）ので、
  カウントが 0 に戻ってランキングから消える。要望は「プロンプト」単位の累計

加算は SQL 関数 `increment_shared_copy(token)` で行う（PostgREST は `col = col + 1` を
書けない）。有効なトークン・ゴミ箱でない場合だけ効き、結果は返さない
（停止済みトークンの存在確認に使わせない）。`service_role` にだけ EXECUTE を与え、
`PUBLIC / anon / authenticated` からは明示的に REVOKE する。
0004 / 0005 の既定権限は TABLES / SEQUENCES にしか効かず、関数は Supabase の既定で
PUBLIC に EXECUTE が付くため。

### 3. 未認証の経路が 3 本になる。読む列はビューで閉じる

| 経路 | 向き | 入口 |
|---|---|---|
| `/s/<token>` | 読み | `src/features/prompts/shares.ts`（0007） |
| `/ranking` | 読み | `src/features/ranking/queries.ts` → ビュー `shared_prompt_ranking` |
| コピー時の +1 | 書き | `src/features/ranking/actions.ts` → 関数 `increment_shared_copy` |

ランキングが読んでよい列は **ビュー `shared_prompt_ranking` で DB 側に固定**する:
`token, copy_count, last_copied_at, title, snippet(本文の冒頭 120 文字), tags`。
`id` / `owner_id` は含めない。全文は `/s/<token>` で読める。
アプリ側のクエリはビューを `select` するだけで、列を足すには migration が要る。

書き込み側は `createPublicAction`（認証しない Server Action ラッパー）を新設して通す。
検証はトークン形式（`isShareToken`）だけで、あとは関数側の条件に任せる。

### 4. カウンタは水増しできる。MVP として受け入れる

同じブラウザで 1 回に抑えるのは `localStorage` の印だけで、消せば何度でも数えられる。
サーバー側の防御は「形式が正しい・有効な共有・ゴミ箱でない」の 3 点のみ。
IP やレート制限は入れない（個人用アプリの規模で、上位に入ることの見返りが無いため）。
不正が問題になったら、その時点で日別テーブル + 制限を別 ADR で足す。

### 5. `/ranking` だけ Service Worker でキャッシュする

SW は「ページを一切キャッシュしない」方針だった（別アカウントや古い状態が出るため）。
ランキングは公開データなので、この 1 ページだけ例外にする:

- `/ranking` への画面遷移: ネットワーク優先。成功したら保存し、失敗したら最後の保存を返す
- `/_next/static/*`: キャッシュ優先。ハッシュ付きでユーザーデータを含まない。
  これが無いとオフラインでは CSS / JS の無い素の HTML になる
- ページに取得時刻を埋め込み、オフラインのときだけ「最後に取得: …」を出す

副作用として、ログイン中に開いた `/ranking`（100 位まで + ヘッダーのアバター）が
そのブラウザに残る。ログアウト後にオフラインで開くと、その版が出る。
公開データ + 本人のブラウザに限られるので受け入れる。

## 却下した代替案

- **`prompts.shared_copy_count` 列**: 上記のトリガー問題。トリガーを条件付きにする手も
  あるが、他の更新経路すべてに影響する変更をカウンタのためにしたくない
- **`/prompts` の中のビュー（ログイン必須）**: 10 位まで誰でも、を満たせない
- **直近 30 日集計**: 日別テーブルと集計が要る。まず累計で出し、必要なら足す
- **ランキング JSON を localStorage に保存する方式**: ページの HTML が無ければ
  オフラインではそもそも画面が出ない。結局 SW でページを持つ必要がある

## 影響

- 新 migration `20260909140000_shared_copy_ranking.sql`
  （テーブル・関数・ビュー・権限）。本番へは Supabase MCP で適用し、
  型は `supabase gen types --linked` で再生成
- 新ルート `/ranking`（`(protected)` の外。未ログイン 10 件、ログイン 100 件）
- `CopyButton` に `onCopied` を追加。共有ページは `ShareCopyButton` で包む
- `public/sw.js` にランキングと静的アセットのキャッシュを追加（キャッシュ名を更新）
- `docs/auth-and-permissions.md` / `CLAUDE.md` / `shares.ts` の
  「唯一の未認証経路」の記述を 3 本に改める
- ローカルに Supabase が無い環境では、コピー→加算→ランキングの通しと
  オフライン動作は検証できない。e2e（`/ranking` の表示）は CI で走る
